## DVR Goal

DVR, Decode-Verify-Rollback, is a deterministic inference optimization.

For pure-attention models, decode and prefill can already be made deterministic,
but DVR can still be faster than repeatedly using prefill-like paths by drafting
with decode and verifying with prefill.

For hybrid models with recurrent or linear-RNN layers, such as GDN/Mamba/KDA,
decode and prefill can diverge because recurrent state is updated through
different numerical paths. DVR must make returned tokens and returned logits come
from a prefill-equivalent verify path while keeping decode as the cheap draft
producer.

## Reference Branch Flow

The reference implementation is structurally similar to simplified EAGLE:

1. The target model is reused as the draft model.
2. Draft tokens are generated by normal self-model decode.
3. Verification is performed by a target prefill/verify path.
4. The speculative layout is chain-only: `topk == 1`.
5. Acceptance is expected to be very high because draft and target are the same
   model, modulo numerical differences and sampling details.

For this port, keep chain-only DVR. Reject sampling from the reference branch is
not required for the first clean implementation; it mainly tries to improve
acceptance, while the self-model chain path should already be near 1.0.

## Key State Semantics

Self-model draft decode mutates target-model state:

- attention KV cache grows;
- GDN/Mamba SSM state is updated in-place;
- Mamba conv state is updated in-place.

Therefore draft must be rollback-safe. After draft, the system must restore the
state that corresponds to the verify start.

FLA chunkwise scan is deterministic only when the verify start is aligned to
`CHUNK_SIZE`. In the tested GDN setup, `CHUNK_SIZE == 64`.

Target verify must start from a `CHUNK_SIZE` boundary. Tokens after that boundary
are kept in a pending buffer until enough accepted tokens accumulate to close
the next chunk.

## GDN DVR Design From Reference

The reference branch's GDN strategy is:

1. Target verify consumes `CHUNK_SIZE + num_draft_tokens` logical tokens.
2. During verify, cache GDN inputs q/k/v/g/beta for accepted/pending tokens.
3. Do not store full intermediate SSM state for every token because it is too
   large.
4. After acceptance is known, advance a per-request pending position.
5. If pending accepted tokens reach `CHUNK_SIZE`, run FLA chunkwise scan for the
   first `CHUNK_SIZE` tokens to update persistent mamba/GDN state.
6. Shift any tail tokens after the chunk boundary back to the front of the
   intermediate q/k/v/g/beta buffers.
7. The next target verify again starts at a `CHUNK_SIZE`-aligned state.

This is the right high-level direction for v3. The exact reference code is too
intrusive and should be simplified.

## What Not To Port

Do not initially port:

- broad FLA rewrites unless a tiny wrapper option is unavoidable;
- reject sampling;
- large unrelated deterministic inference changes;
- reference branch's broad historical changes outside DVR/GDN touchpoints;
- ref/v2 worker structure.

The FLA in-place problem can be handled by explicit backup/restore or by using a
scratch state slot during verify/post-verify. Only add an FLA wrapper flag if the
clean state protocol cannot avoid side effects.

   prefill-equivalent chunkwise path, and avoid permanent mutation until commit.
10. After accepted tokens reach `CHUNK_SIZE`, recompute and commit persistent
    recurrent state for exactly one chunk, then shift the tail.
11. Validate Qwen3.5-0.8B with random lengths beyond 64 and batched requests.

## Minimal Correctness Invariants

- DVR draft provider `self` must have acceptance close to 1.0.
- `num_draft_tokens` controls per-round draft length; it is unrelated to the
  user API's `max_new_tokens`.
- Returned client logprobs must equal full-prefill scoring logprobs.
- Verify starts must be `CHUNK_SIZE` aligned for GDN/KDA/Mamba chunkwise state.
- Draft decode state mutations must be rolled back before target verify.
- Persistent recurrent state is updated only at committed chunk boundaries.
- Tail tokens after the last committed chunk remain buffered for the next round.
